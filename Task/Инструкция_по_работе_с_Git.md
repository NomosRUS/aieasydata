## **Инструкция по командной работе в GitHub**

Эта методология поможет нам работать параллельно, не мешая друг другу, и интегрировать наши модули (валидация, агрегация, оптимизация и хранилище) в единый работающий продукт.

### **Основная модель ветвления (Branching Model)**

Мы будем использовать две основные ветки и множество временных:

1.  `main`  — **Священная ветка**. Здесь находится только стабильный, протестированный и рабочий код. Напрямую в `main`  никто ничего не коммитит. Слияние в `main`  происходит только из `develop` .
2.  `develop`  — **Интеграционная ветка**. Это основная рабочая ветка проекта. В ней собираются все готовые и протестированные фичи от разработчиков. Именно из неё мы будем создавать свои ветки для задач.
3.  **Feature-ветки** (`feature/название-задачи` ) — Временные ветки для каждой конкретной задачи. Например: `feature/data-validation-module`  или `feature/api-performance-metrics` .

### **Пошаговый процесс работы для каждого разработчика**

**Шаг 1: Подготовка к работе (делается один раз в начале)**

Каждый разработчик должен иметь актуальную версию `develop` .

```bash
# 1. Переключиться на ветку develop
git checkout develop

# 2. Загрузить самые последние изменения с GitHub
git pull origin develop
```

**Шаг 2: Создание ветки для своей задачи**

Никогда не работайте напрямую в `develop` ! Для каждой новой подзадачи (например, "реализация базовой валидации") создавайте новую ветку от `develop` .

```bash
# 1. Убедитесь, что вы на актуальной ветке develop
git checkout develop
git pull origin develop

# 2. Создайте новую ветку для своей задачи
# Формат: feature/module-name-feature-description
git checkout -b feature/validation-base-checks
```
*Примеры имен веток:*
*   `feature/aggregation-join-logic` 
*   `feature/performance-metrics-collector` 
*   `feature/warehouse-ddl-generator`  (ваша ветка)

**Шаг 3: Работа в своей ветке**

Теперь разработчик может спокойно писать код, делать коммиты, экспериментировать. Эти изменения изолированы и никому не мешают.

```bash
# ...пишем код...

# Делаем коммиты как можно чаще с понятными сообщениями
git add .
git commit -m "feat(validation): add missing values check"
```

**Шаг 4: Синхронизация с `develop`  (КЛЮЧ К ПРЕДОТВРАЩЕНИЮ КОНФЛИКТОВ)**

Раз в день (или перед тем, как создавать Pull Request) необходимо подтягивать изменения из `develop`  в свою feature-ветку. Это позволяет решать небольшие конфликты по мере их поступления, а не разгребать один огромный конфликт в конце.

Мы будем использовать `rebase`  — это делает историю коммитов чистой и линейной.

```bash
# 1. Переключиться на develop и обновить её
git checkout develop
git pull origin develop

# 2. Вернуться в свою ветку
git checkout feature/validation-base-checks

# 3. Применить изменения из develop ПОВЕРХ своих
git rebase develop
```
**Что такое `rebase` ?** Он "перемещает" начало вашей ветки на самую свежую версию `develop` , а затем накатывает ваши коммиты один за другим. Если на каком-то шаге возникнет конфликт, Git остановится и попросит вас его решить.

**Шаг 5: Создание Pull Request (PR) для интеграции**

Когда задача в ветке полностью готова (например, реализован "базовый уровень" модуля), разработчик создает **Pull Request** (Запрос на слияние) в ветку `develop` .

1.  Сначала нужно отправить свою ветку на GitHub:
    ```bash
    git push origin feature/validation-base-checks
    ```
2.  Зайти в интерфейс GitHub. Там появится плашка "Create a pull request".
3.  **Правила оформления Pull Request:**
    *   **Цель (Base):** `develop` . **Источник (Compare):** ваша `feature/*`  ветка.
    *   **Название:** Краткое и понятное (например, "Реализация модуля валидации данных").
    *   **Описание:** Что сделано? Как это связано с общей задачей? Как это протестировать?
    *   **Reviewers (Рецензенты):** Обязательно назначьте меня (тимлида) и, возможно, еще одного разработчика, чей модуль тесно связан с вашим.

**Шаг 6: Code Review (Проверка кода)**

Это ваша, как тимлида, основная точка контроля качества.

*   Ни один PR не вливается в `develop`  без вашего одобрения (`Approve` ).
*   Вы (и другие рецензенты) оставляете комментарии прямо в коде на GitHub.
*   Разработчик вносит исправления в своей же ветке и делает новые коммиты. PR обновится автоматически.

**Шаг 7: Слияние (Merge) Pull Request**

После одобрения PR, автор или тимлид нажимает кнопку **"Squash and merge"** в интерфейсе GitHub.

*   **Почему "Squash and merge"?** Этот режим "схлопывает" все коммиты из feature-ветки в один большой коммит в `develop` . Это делает историю `develop`  очень чистой: один коммит — одна фича.
*   После слияния временную feature-ветку можно удалить.

### **Как решать проблему противоречивых изменений?**

Ваша главная проблема — это **конфликты слияния (merge conflicts)**. Вот как их минимизировать:

1.  **Общие интерфейсы и контракты API.** В самом начале договоритесь о "контрактах" между вашими модулями.
    *   В репозитории уже создали папку `contracts`  или `shared_schemas` .
    *   В ней разместили Pydantic-модели для API-запросов и ответов. Например, `DataQualityReport.py` , `AggregationRequest.py` .
    *   Все разработчики импортируют модели из этого общего места. Если кто-то меняет контракт, он обязан предупредить всех остальных. Это предотвратит логические конфликты.

2.  **Частая синхронизация.** Правило №1 — `git rebase develop`  (Шаг 4) нужно делать **часто**. Лучше решить 3 маленьких конфликта за неделю, чем один гигантский в последний день.

3.  **Разделение кода.** Старайтесь не редактировать одни и те же файлы. Поскольку у вас модульная архитектура, это будет несложно. Если все же нужно работать в одном файле (например, docker-compose.yml), предупреждайте друг друга.

4.  **Мокирование (Mocking).** Если модуль Разработчика 1 зависит от API, который делает Разработчик 2 (и который еще не готов), Разработчик 1 не должен ждать. Он должен "замокать" этот API — то есть создать фейковый ответ, который имитирует работу настоящего.
